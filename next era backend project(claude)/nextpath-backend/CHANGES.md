This documents exactly what was changed, moved, or added relative to the files Codex produced. Anything not listed here was copied over unchanged.

## 1. Files moved into a real Next.js App Router structure

Codex's files were flat, uploaded with underscore/space names instead of the paths Next.js and the project's own imports/config expect. No code inside these files was changed — only their location.

| Codex's file | Moved to |
|---|---|
| `eligibility_types.ts` | `src/lib/eligibility/types.ts` |
| `eligibility_evaluator.ts` | `src/lib/eligibility/evaluate.ts` |
| `eligibility_test.ts` | `src/lib/eligibility/evaluate.test.ts` |
| `health_route.ts` | `src/app/api/health/route.ts` |
| `next_config.ts` | `next.config.ts` (project root) |
| `vitest_config.ts` | `vitest.config.ts` (project root) |
| `_env.example` | `.env.example` (project root) |

This placement wasn't arbitrary — `evaluate.test.ts` imports from `./evaluate` and `./types`, and `vitest.config.ts`'s `include: ["src/**/*.test.ts"]` only picks up test files that actually live under `src/`. Next.js's App Router also requires API routes to be a `route.ts` file inside `src/app/api/<path>/`, which is why `health_route.ts` became `src/app/api/health/route.ts` rather than keeping its original filename.

## 3. `vitest.config.ts` — one addition, and it fixes a real bug

```diff
+import { fileURLToPath } from "node:url";
+
 import { defineConfig } from "vitest/config";

 export default defineConfig({
+  resolve: {
+    alias: {
+      "@": fileURLToPath(new URL("./src", import.meta.url))
+    }
+  },
   test: {
     environment: "node",
     include: ["src/**/*.test.ts"]
   }
 });
```

`tsconfig.json` defines a `"@/*": ["./src/*"]` path alias, which `tsc --noEmit` and Next's bundler both understand natively. Vitest does not read `tsconfig.json` paths on its own — it needs its own `resolve.alias`. This wasn't caught by typechecking (which passed before this fix); it only surfaced when the new route test below tried to `import ... from "@/lib/eligibility/evaluate"` and Vitest failed with `Cannot find package '@/lib/eligibility/evaluate'`. Fixed by adding the alias here.

## 7. Authentication foundation added (increment 3 — Codex did not provide any of this)

Codex's code had no notion of who was calling the API: there was a Supabase client factory, a `profiles` table keyed by `auth.users.id`, and an RLS policy that gated reads on `auth.uid() = id`, but nothing translated an incoming HTTP request into a verified user. Without that, no route could safely answer "what's *my* profile?" or run eligibility against *my* row. This increment adds that translation.

### Files added

- **`src/lib/auth/getCurrentUser.ts`** — the only auth entry point. Reads `Authorization: Bearer <jwt>` from the incoming `Request`, calls `client.auth.getUser(jwt)` to validate it through Supabase's Auth server, and returns one of two discriminated-union variants: `{ status: "authenticated", userId, user, client }` or `{ status: "unauthenticated", reason: "missing_credentials" | "invalid_token", message }`. On success it builds a fresh, per-request Supabase client with `accessToken: async () => verifiedJwt` and `persistSession: false`, so every PostgREST call on that client carries the user's JWT in its `Authorization` header — which is what makes the existing `auth.uid() = id` RLS policies actually gate data per-user. See `docs/get-current-user.md`.
- **`src/lib/auth/getCurrentUser.test.ts`** — seven tests covering: a valid JWT returning the user, the token being forwarded verbatim to Supabase, no `Authorization` header returning `missing_credentials` with zero Supabase calls, a non-Bearer scheme returning the same, Supabase returning an error returning `invalid_token`, Supabase returning `{ user: null }` with no error also returning `invalid_token`, and the returned client exposing `auth` for downstream repository wiring. Uses an injected mock that records every `auth.getUser` call so a test can assert the helper never trusts an unverified id.

### Why bearer-token, not cookie/SSR

`@supabase/ssr` isn't a dependency, the frontend doesn't exist yet, and neither approach is established in the project — so this helper chooses one, states the choice prominently in its docs, and keeps the interface narrow enough that swapping later (e.g. when the frontend picks a session-cookie model) is a single-file change. Bearer is also the more explicit model when the frontend is a separate app: the JWT is already in memory after `signIn`, so requests carry their credential with them without needing cookie plumbing.

### Files modified

- **`src/lib/supabase/client.ts`** — added a `getSupabaseConfig()` helper that returns `{ url, publishableKey }` after running the same env-var checks. `getSupabaseClient()` now reads through it (no behaviour change for existing callers), and `getCurrentUser` uses it to build per-request authenticated clients. See `docs/supabase-client.md`.
- **`docs/supabase-client.md`** — documented the new `getSupabaseConfig()` helper.
